Hand repetitive work to tools: three small habits

I used to misunderstand “being productive”. I thought it meant learning some impressive skill or installing a complicated methodology. After some flailing, I found that what actually saves time is often a few tiny, concrete judgments.

Here are the three habits I reach for most these days.

1. Do the math before you start: how many more times will I do this?

Before starting anything, I ask myself one question: is this the last time I'll do it?

If the answer is “probably ten more times”, then doing it manually is a loss. If the answer is “once in my life”, then spending two hours writing a script is the loss.

A real example. While tidying up files, I had a batch of files with messy names, like this:

Renaming them one by one takes about forty minutes and is annoying. Writing a script to rename them takes twenty-five minutes the first time. Manual looks faster.

The catch: I do this kind of cleanup every month. After three times, the script has paid for itself; every run after that is pure profit.

So the criterion isn't “which is faster right now”, it's comparing cost per run × expected runs against automation cost + maintenance cost. The math doesn't need to be precise — just enough to see the order of magnitude.

2. Write the rules down, don't keep them in your head

The second habit is simpler, but pays off the most: turn anything that needs a decision into a rule you can restate.

I've noticed that many people (myself included) re-make the same decision every time they do repetitive work. Take file sorting: every time I stopped to think “does this count as reference material? Which folder?” — thirty times, each slightly different, until the folder was a mess.

The fix: spend ten minutes writing the rules down.

  • Dated invoices always go into “Finance / year”;
  • Naming always follows “YYYYMMDD_topic”, which fixes sorting at the source;
  • Anything uncertain goes into “To sort”, cleared once a week.

Once written down, three things improve:

  1. Decisions become lookups — much faster, no more agonizing;
  2. Results stay consistent, so later you can find things by search instead of memory;
  3. The rules can be handed to tools, so a script or AI executes them.

If you can't state the decision rule in one sentence, you haven't thought it through — handing it to a tool then only produces chaos faster.

3. Always leave yourself a way back

This one I learned the hard way.

Once I wrote a batch-processing script, tested it on two files with great results, then ran it straight on a whole folder. Afterwards I found a boundary case the rules didn't cover, and some files had been rewritten into the wrong format.

Worse: I had no backup.

I spent an entire evening recovering them, file by file, using size and modified time. Since then I've kept three hard rules for myself:

  • Test on a small batch first. Two files working doesn't mean two hundred will;
  • Keep a copy before changing anything. Even a temporary copy in another directory beats nothing;
  • Print a preview before destructive operations. Have the script output “here's what I will change” first, then decide whether to run it.

It looks like just a few extra steps, but when something does go wrong, those steps are the distance between you and disaster. Automation amplifies errors, not just efficiency — one wrong run is two hundred wrong runs.

The part automation can't solve

For all the benefits, I have to be clear about its limits. Tools can execute for you, but they can't make three kinds of decisions:

Tools can'tWhy
Judge whether the goal is rightYou automate something you shouldn't be doing at all — you're just doing the wrong thing faster
Handle exceptionsRules always miss some cases; boundaries need a human to set them
Own the outcomeWhen things break, nobody goes looking for the script's responsibility

So my position now is: hand execution to tools, keep judgment for myself.

Tools remember formats, process batches, and spare me repetitive motions; I'm responsible for knowing what I want, where the boundaries are, and how to roll back when something breaks. Once you separate those two, the efficiency gain is just a by-product.

If you remember only one line: figure out the rules first, then hand them to the tool; leave a way back first, then press run.

Leave the rest to time.
